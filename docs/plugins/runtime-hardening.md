# plugin runtime hardening

the plugin runtime opts into `JS_SetNativeWorkLimit` with eight million work units per operation. zero remains the default for widgets. allowance resets do not clear the runtime stop latch. native call entry checks the host deadline; instrumented native work checks it at least every 1024 charged units. generic array length traversal is charged up front, including sparse objects with lengths far above their actual allocation. string buffer writes, property traversal, array/typed-array sort comparisons, string search/replace/trim, quadratic bigint operations, source/json tokenization and regexp timeout callbacks charge work. unicode decomposition, combining-character insertion sorting, composition and utf-32 conversion also charge work; case conversion polls while scanning the final-sigma context. conservative estimates can reject expensive valid inputs with a visible runtime failure.

sorts use an interrupt-aware comparator and a comparison-count estimate before entry. after cancellation the underlying sorter can still finish its bounded comparator/cleanup path, with comparisons returning zero. bigint multiplication, division, conversion and string search use conservative preflight cost bounds rather than inserting a callback into every arithmetic instruction. regexp catastrophic backtracking uses its existing timeout callback connected to the plugin work policy. the default interpreter poll interval and the default widget policy are unchanged.

runtimes start only once the app reports the foreground, never on a background launch, and stop when it leaves it. operation budgets are thread cpu time: one second for activation and 250 milliseconds for callbacks, so a plugin whose thread waits for a core on a busy device is not stopped for it (the `descheduled` scenario). a wall-clock backstop of eight times the budget, at least two seconds, remains. each operation preserves its remaining budgets across native awaits. waiting pauses only when the current task is pending, the job queue is empty and an actual tracked native request exists. an unresolved pure promise does not pause: with no queued job and no tracked native request nothing can settle it (plugins have no timers), so the operation fails at once with unresolved_promise. pending native requests do not pause an executing javascript loop or a microtask storm. total native waiting is limited to 60 seconds per operation. request ids are positive safe integers, tracked in a bounded native set of 64 entries. only a known reply resumes its waiter; unknown or duplicate replies do not create work.

the cumulative cpu budget is two seconds per 60-second window. windows, which only the test suites use, reads QueryThreadCycleTime and converts cycles with the processor's nominal frequency (registry `~MHz`), falling back to GetThreadTimes, which charged a fully running thread only 28–66 % of the wall time; apple uses thread_info on the current pthread's mach thread, and other posix hosts use CLOCK_THREAD_CPUTIME_ID. each synchronous engine entry measures its own thread, allowing a serial dispatch queue to move between threads. paused native waits and unrelated work between entries are not counted. failure to read the thread clock stops execution. clock resolution and scheduling affect measurements; this is a sampled quota, not a real-time preemption guarantee.

the swift wrapper runs every engine call on the runtime's own thread (`DGPluginRuntimeThread`, a 4 MiB stack), never on a dispatch queue. quickjs's 512 KiB stack limit stops a runaway recursion only when the real stack is larger than the limit plus the native frames around its checks; dispatch worker threads have 512 KiB stacks, so a deep recursion or deeply nested JSON.parse reached the guard page and crashed the app. the message widget pool uses dedicated 8 MiB threads for a 2 MiB limit for the same reason. the wrapper keeps the native pointer in a retained handle. stop and pointer detachment share a lock; engine access/destruction remain on the runtime thread, which ends after deinitialization drains it. deinitialization captures the retained handle and callback context, without sending a raw OpaquePointer through the asynchronous closure. initialization publishes the reply closure before any plugin execution. a pending operation rejects overlapping dispatch with runtime_busy rather than replacing its promise task.

`Tests/run_tests.py` (any clang or gcc; the "Plugin runtime tests" workflow runs it on macos-26) and `run-tests.ps1` (visual studio clang) build the actual vendored engine and c host, verifies the canonical crlf-to-lf engine lock and embedded bootstrap, then uses a python subprocess watchdog. each hostile scenario has its own child process with a ten-second kill timeout; the original regression process has twenty seconds. bazel exposes each scenario as a separate short-timeout test in `DGPluginNativeWorkTests`.

the existing quickjs smoke and host suites also passed against the rebuilt engine, including the stock interpreter interrupt-rate assertion. the windows smoke executable needs an eight-mib os stack reservation because its unchanged fixture requests a two-mib interpreter stack; the default one-mib windows executable stack is smaller than the fixture. the script sets that reservation for those test executables and runs them under fifteen-second subprocess watchdogs. this is a test harness setting, not an engine or widget policy change.

the final observed run passed the original regression process and 25 isolated cases: huge sparse join/reverse/sort, catastrophic regexp, costly replace/sort/stringify/parse/repeat/trim/bigint, typed-array sort, repeated linear regexp, pending microtask storm, unresolved pure promise, uncatchable native stop, legitimate 1.2-second native wait, cancellation while waiting, accumulated active deadline, rolling cpu budget, cancellation during join/regexp, compile-only interruption, adapter wrapper errors and default policy parity. native cancellation measured 3–4 ms, catastrophic regexp 87 ms, parse 160 ms and cpu-window exhaustion 2030 ms on the current windows host. repeated linear regexp was stopped by the real heap limit, so that fixture does not establish regex polling latency. the actual swift runtime and embedded bootstrap also passed windows swift 6.4.2 type checking without the previous raw-pointer capture warning.

remaining limits: cooperative polls do not make arbitrary native code preemptive. allocation/garbage-collection cleanup and other uninstrumented internal functions still need a broader adversarial audit. current fixtures establish their named paths, not exhaustive interruption of every native builtin. apple thread-clock compilation, full ios integration and device behavior remain unverified on windows. no interpreter bug or native decoder defect is isolated from the app process.

a rejected dispatch is the plugin's own error, not a runtime failure. when the promise of a command, event, page callback or transform is rejected, the host ends that operation like a fulfilled one once its detached work drains, keeps the runtime and reports the error's code through `dgjs_rejection()`. the code is read only from an own data property of an Error object, so no plugin getter or proxy runs (`rejection_getter`). a rejected module evaluation or activate() still stops the runtime. the manager reports a rejected command to its caller, keeps the draft for a rejected outgoing handler and stops a plugin only after five rejected events in a row, three failed transforms or three failed outgoing handlers in a row. an outgoing send waits for a plugin that is busy with other work, up to its three-second deadline, which then keeps the draft without stopping the plugin; only a handler still running at the deadline stops it. budget, memory and cancellation stops still turn it off.

a runtime that is starting is listed in `running.json` beside the plugin state, from its start until ten seconds after a successful activation or until it stops. a launch that still finds an entry there turns that plugin off with a recorded reason instead of starting it again, so a plugin that crashes the app in activate() or in the events right after cannot crash every launch, while a later unrelated crash or a dead battery turns nothing off.

command and transform ids and their quota slots are reserved before native registration replies, rolled back on refusal and retained until native unregister succeeds. repeated disposal shares its pending request, and a refused disposal can retry. event names share one pending native subscription, while every listener registration owns a distinct token, even for the same handler. quotas are checked before the native side effect. resubscription waits for a pending unsubscribe; stale disposal never removes a new subscription.

the review regression run passed 45 isolated scenarios plus the original runtime, quickjs smoke and quickjs host suites on windows. the added cases cover concurrent command registration and quotas, transform disposal races and retry, native refusals and retry, independent listener ownership, stale disposal, unsubscribe/resubscribe ordering, event quotas, unicode values, hostile normalization/locale comparison/case conversion and cancellation during normalization. normalization and locale comparison exhausted their native allowance in about 55 ms; cancellation during normalization returned in 3 ms. the normalization cases require native_work_limit rather than a late execution_timeout, and cancellation has a 500 ms upper bound. restoring the old bootstrap fails the lifecycle cases.
