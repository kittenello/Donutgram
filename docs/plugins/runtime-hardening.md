# plugin runtime hardening

the plugin runtime opts into `JS_SetNativeWorkLimit` with eight million work units per operation. zero remains the default for widgets. allowance resets do not clear the runtime stop latch. native call entry checks the host deadline; instrumented native work checks it at least every 1024 charged units. generic array length traversal is charged up front, including sparse objects with lengths far above their actual allocation. string buffer writes, property traversal, array/typed-array sort comparisons, string search/replace/trim, quadratic bigint operations, source/json tokenization and regexp timeout callbacks charge work. conservative estimates can reject expensive valid inputs with a visible runtime failure.

sorts use an interrupt-aware comparator and a comparison-count estimate before entry. after cancellation the underlying sorter can still finish its bounded comparator/cleanup path, with comparisons returning zero. bigint multiplication, division, conversion and string search use conservative preflight cost bounds rather than inserting a callback into every arithmetic instruction. regexp catastrophic backtracking uses its existing timeout callback connected to the plugin work policy. the default interpreter poll interval and the default widget policy are unchanged.

wall budgets are one second for activation and 250 milliseconds for callbacks. each operation preserves its remaining active wall budget across native awaits. waiting pauses only when the current task is pending, the job queue is empty and an actual tracked native request exists. an unresolved pure promise does not pause. pending native requests do not pause an executing javascript loop or a microtask storm. total native waiting is limited to 60 seconds per operation. request ids are positive safe integers, tracked in a bounded native set of 64 entries. only a known reply resumes its waiter; unknown or duplicate replies do not create work.

the cumulative cpu budget is two seconds per 60-second window. windows uses GetThreadTimes, apple uses thread_info on the current pthread's mach thread, and other posix hosts use CLOCK_THREAD_CPUTIME_ID. each synchronous engine entry measures its own thread, allowing a serial dispatch queue to move between threads. paused native waits and unrelated work between entries are not counted. failure to read the thread clock stops execution. clock resolution and scheduling affect measurements; this is a sampled quota, not a real-time preemption guarantee.

the swift wrapper keeps the native pointer in a retained handle. stop and pointer detachment share a lock; engine access/destruction remain on the owned serial queue. deinitialization captures the retained handle and callback context, without sending a raw OpaquePointer through the asynchronous closure. initialization publishes the reply closure before any plugin execution. a pending operation rejects overlapping dispatch with runtime_busy rather than replacing its promise task.

`run-tests.ps1` builds the actual vendored engine and c host, verifies the canonical crlf-to-lf engine lock and embedded bootstrap, then uses a python subprocess watchdog. each hostile scenario has its own child process with a ten-second kill timeout; the original regression process has twenty seconds. bazel exposes each scenario as a separate short-timeout test in `DGPluginNativeWorkTests`.

the existing quickjs smoke and host suites also passed against the rebuilt engine, including the stock interpreter interrupt-rate assertion. the windows smoke executable needs an eight-mib os stack reservation because its unchanged fixture requests a two-mib interpreter stack; the default one-mib windows executable stack is smaller than the fixture. the script sets that reservation for those test executables and runs them under fifteen-second subprocess watchdogs. this is a test harness setting, not an engine or widget policy change.

the final observed run passed the original regression process and 25 isolated cases: huge sparse join/reverse/sort, catastrophic regexp, costly replace/sort/stringify/parse/repeat/trim/bigint, typed-array sort, repeated linear regexp, pending microtask storm, unresolved pure promise, uncatchable native stop, legitimate 1.2-second native wait, cancellation while waiting, accumulated active deadline, rolling cpu budget, cancellation during join/regexp, compile-only interruption, adapter wrapper errors and default policy parity. native cancellation measured 3–4 ms, catastrophic regexp 87 ms, parse 160 ms and cpu-window exhaustion 2030 ms on the current windows host. repeated linear regexp was stopped by the real heap limit, so that fixture does not establish regex polling latency. the actual swift runtime and embedded bootstrap also passed windows swift 6.4.2 type checking without the previous raw-pointer capture warning.

remaining limits: cooperative polls do not make arbitrary native code preemptive. unicode normalization/case-conversion helper algorithms, allocation/garbage-collection cleanup and other uninstrumented internal functions still need a broader adversarial audit. current fixtures establish their named paths, not exhaustive interruption of every native builtin. apple thread-clock compilation, full ios integration and device behavior remain unverified on windows. no interpreter bug or native decoder defect is isolated from the app process.
